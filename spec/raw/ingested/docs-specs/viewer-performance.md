# Viewer: performance on large projects

Status: implemented (issue #2)

## Goal

Expanding, re-sorting, hovering and scrolling stay responsive on projects with tens of thousands of
dependencies. Before this change the viewer created a DOM row for every visible tree row and an SVG
path (plus a hit path) for every arc on every change. On a model with ~10,000 rows and ~38,000 arcs
at member level, expanding to members took about 2 s, re-sorting about 1.9 s and hovering a row
about 0.6–1 s (headless Chrome, style and layout included).

## Constraints

- No dependencies, no build step, one self-contained HTML file (unchanged).
- Behaviour, layout and looks unchanged: same rows, same arc geometry (`viewer-arcs.md`), same
  colours, the same scroll height and width, highlighting, selection, find, drag & drop.
- `document.body.dataset.rows/arcs` still count all rows and arcs of the tree, not only the ones in
  the DOM (the smoke test reads them).

## Behaviour

- **Virtualised rows.** The tree is laid out in full (row index → `top = index × rowHeight`), but
  only the rows in a window around the visible part of the scroll area are in the DOM: the rows in
  view plus a margin of several screens above and below. Scrolling re-renders the window when the
  visible part gets close to its edge.
- **Arcs in the window only.** Arcs are computed for the whole tree (they are needed for counts,
  hover peers and the panel), but only arcs whose row range overlaps the window are drawn, with
  anchors on rows in the window. An arc with at least one end in the window, or belonging to the
  selection (selected arc, or arcs of the selected row), is drawn on its own with arrowhead, hit path
  and hover. An arc that only passes through the window (both ends outside) is still drawn, but
  bundled with the others of its colour into one path per stroke width (rounded to 0.25px): long
  arcs all bulge to the same capped width, so they draw nearly the same lines, and their arrowheads
  are off-screen. They are hovered and clicked where they end. Bundled arcs are drawn below single
  ones.
- **Tooltips** of arcs are created on first hover instead of for every arc up front.
- **Hover and selection** only touch elements in the DOM and are applied when the window
  re-renders, so a highlighted arc or row scrolled into view is shown highlighted.
- **No needless work.** Changing only the expansion (toggle a row, Packages/Files/Types/Members)
  does not levelize again (as before). Label widths are measured once per name and cached. The
  nearest visible ancestor of every node is computed once per layout instead of per edge.
- `?bench` (embedded data only): after loading, the viewer clicks Files, Types, Members, A–Z,
  Levelize, hovers a row and scrolls to the middle, and publishes each time in ms (including style
  and layout) plus the number of DOM rows and arcs as JSON in `document.body.dataset.bench`. The
  initial render's pending layout is flushed first and reported as `load`.

## Checkable statements

On the synthetic model generated by `test/gen_large.py` (660 files, 2,940 types, 8,820 members,
57,000 dependencies; about 10,000 rows and 38,000 arcs at member level), in headless Chrome with a
1400×1000 window:

- Members, A–Z and Levelize each take less than 200 ms on a developer machine. `scripts/check.sh`
  fails above 500 ms, leaving room for slower CI machines while still catching a return to
  rendering everything (≈2,000 ms).
- Hover and scroll take about 50 ms or less (check fails above 150 ms).
- At member level, fewer than 1,000 rows and fewer than 5,000 arcs are in the DOM.
- The fixture checks (rows, arcs, groups, Kotlin rows, arc geometry) still pass.

Measured after the change (same machine as the numbers above): Files ~150 ms, Types ~165, Members
~115, A–Z ~170, Levelize ~160, hover ~40, scroll ~50; 165 rows and ~1,100 arcs in the DOM.

## Out of scope

- Faster scanning or a smaller JSON.
- Paint time (not measurable without a DevTools client; the DOM size bounds it).
- Levelization speed beyond what the measurements require.
